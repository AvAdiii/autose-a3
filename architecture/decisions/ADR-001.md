# ADR-001: Five narrow agents for five stages, deterministic code for release and routing

- **Decision area:** D1, splitting the work
- **Status:** Accepted (2026-11-21)

## Context

The workflow has six fixed stages. Each stage needs different information, different tools and a
different attitude: the analyst must not design, the tester must not shape tests around the code it
is testing, and the reviewer must not share the builders' assumptions. In A2 a single agent did
everything in one context: on the hardest task (T3) all six runs used up the 30-minute budget after
86-107 tool calls without finishing, and in T1 with the architecture document two runs left
regressions (mean 1.5) that the agent's own testing did not catch. Python-Markdown changes are small (one to three files), so
one agent could hold the whole task in context; the question is not capacity but separation of
concerns and blast radius.

Three shapes were on the table:

1. **One agent for everything** (one long Claude Code session per issue).
2. **One agent per stage** (six agents, including one that "releases").
3. **One agent per stage that needs judgment, deterministic code for the rest.**

## Decision

Use option 3: five agent roles, each a fresh Claude Code session with its own system prompt, tool
list and model, for the stages that need judgment, and plain Python for everything that does not.

| Stage | Who | Why this split |
|---|---|---|
| 1 Requirements | Analyst agent | Reuses the A1 skill unchanged in spirit; must stay ignorant of solutions (A1 boundary rule). |
| 2 Design | Architect agent | Reads `ARCHITECTURE.md`; its output (`design.md`) is the contract the tester and developer share. |
| 3 Implementation | Developer agent | Only role with write access to source files. |
| 4 Testing | Tester agent | Writes tests from the spec and design **without seeing the implementation** (works at the base commit, ADR-003). |
| 5 Release | `release.py` | Push, open PR and wait for CI are API calls with one right answer; a model adds cost and risk and nothing else. |
| 6 Review | Reviewer agent | Separate job, model, prompt and permissions (ADR-008). |

Routing between stages (retry, go back to design, go back after review) is also code, not an agent
(ADR-002). A small, tool-less Haiku "spec judge" assists the stage 1 check but makes no decision
(ADR-007).

## Alternatives considered

- **One agent for everything.** Cheapest in tokens and simplest to build. Rejected because the
  checks become self-checks: the agent that wrote the code writes the tests and grades them, so a
  misreading of the issue passes every gate. It also needs every tool at once (Bash + Edit on all
  paths + the untrusted issue text in context), which is the worst prompt-injection posture
  (ADR-009). A2 showed the drift problem directly.
- **One agent per stage, including release.** Uniform, but a "release agent" with push rights is a
  model holding a write token for no benefit. Also rejected: merging requirements and design into
  one agent, because the A1 skill explicitly forbids design content in the spec and the reviewer
  later needs to judge whether the design fits the requirements independently.
- **Planner agent that picks the next stage.** Discussed in ADR-002.

## Consequences

- Each role gets the minimum tools for its stage, so the guard policy (ADR-005) is short and
  checkable per role.
- Hand-offs happen through artifacts only, so every hand-off is visible on GitHub (ADR-003, ADR-004).
- More sessions means more fixed prompt overhead (system prompt + repository orientation is paid
  five times). Measured in `results/results.csv` as tokens per stage.
- A misunderstanding in the spec propagates to every later stage; only the reviewer (who reads the
  raw issue, not the spec) can catch it. This is intended and is the main reason the reviewer does
  not see `spec.md`.
