# ADR-010: Label or `/autose` comment by a write-level collaborator; one active run per issue, queued not cancelled

- **Decision area:** D10, triggers
- **Status:** Accepted (2026-11-21)

## Context

The workflow spends quota and opens PRs, so who can start it matters. The events available are
`issues: labeled`, `issue_comment: created` (fires for issues and PRs), and `workflow_dispatch`.
Two triggers on the same issue (a label and a comment a minute apart, or two maintainers) must not
produce two branches racing to push.

## Decision

**Events.**

| Event | Condition | Starts |
|---|---|---|
| `issues: labeled` | label name is `autose` | full run from stage 1 |
| `issue_comment: created` on an issue | body starts with `/autose` | full run from stage 1; maintainer comments become part of the analyst input (clarifications) |
| `issue_comment: created` on a PR from `autose/issue-N` | body starts with `/autose` | review round from stage 6 on the current PR head, then the normal rework rounds |
| `workflow_dispatch` | inputs `issue`, `start_stage`, `reviewer_variant` | used by maintainers and the experiments (E1, E2) |

**Who.** The gate job asks the API for the sender's permission on the repository
(`GET /repos/{repo}/collaborators/{user}/permission`) and continues only for `admin`, `maintain`
or `write`. Bots (`sender.type == "Bot"`) are ignored, so the workflow's own comments can never
trigger it. Applying a label already needs triage rights, but triage is not enough to start a run.
Rejected triggers get a short reply and no further jobs.

**Concurrency.**
- Workflow-level `concurrency: autose-${{ github.event.issue.number || inputs.issue }}` with
  `cancel-in-progress: false`: a second trigger for the same issue waits for the first run.
- A `/autose` on the PR has a different number than the issue, so the round jobs also carry a
  job-level group keyed on the **issue** number resolved by the gate job.
- GitHub keeps at most one pending run per group; a third trigger replaces the queued second one,
  which is the behaviour we want (the latest request wins, nothing runs twice in parallel).
- Runs for different issues are independent and may run in parallel.

## Alternatives considered

- **Any issue author can start it.** Anyone could spend the quota and push branches. Rejected.
- **`cancel-in-progress: true`.** A maintainer re-labelling would kill a nearly finished run.
  Rejected.
- **`pull_request_target` or `issues: opened`.** Fires on untrusted input automatically. Rejected.

## Consequences

- Starting a run is always a deliberate maintainer action that is visible in the issue timeline.
- The permission check costs one API call per comment on the repository; non-`/autose` comments are
  filtered in the job `if:` before any runner starts.
