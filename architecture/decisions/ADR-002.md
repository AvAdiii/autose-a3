# ADR-002: A deterministic state machine inside jobs, review rounds unrolled as reusable-workflow calls

- **Decision area:** D2, control flow
- **Status:** Accepted (2026-11-21)

## Context

The stages are fixed, but the path through them is not: tests can fail (back to 3), repeated test
failures suggest a bad plan (back to 2), and the reviewer can send work back to 1, 2 or 3. Someone
has to decide when to go back, and the run must provably stop. GitHub Actions adds two constraints:
a job cannot loop back to an earlier job, and privileges are set per job, not per step.

Options:

1. **LLM planner/orchestrator** that reads artifacts and picks the next stage.
2. **Deterministic state machine** in Python, one process per job.
3. **Jobs that trigger each other** with `workflow_dispatch` (each review round a new run).
4. **Static job graph** where each review round is a call to one reusable workflow.

## Decision

Combine 2 and 4.

- Inside the **build job**, `orchestrator.py` is an explicit state machine over stages 1-4.
  Transitions are a table keyed on check results: `spec_ok → design`, `design_ok → implement`,
  `build_ok → test`, `tests_fail → implement` (attempt < 3), `2 consecutive test failures →
  design` (once), `TEST_DISPUTE → tester` (once), anything else `→ stop` with a reason.
- The **review loop** is unrolled in YAML: `autose.yml` calls `autose-round.yml` as round 0,
  then round 1 and round 2 each with `if: needs.<previous>.outputs.verdict == 'request_changes'`.
  Each round = build → release → review jobs. The reviewer's structured verdict is mapped to a
  restart stage by `review.route()` (earliest stage named by a blocking finding), and the
  next round's build job starts there.
- Who decides to go back: **code**, always. Agents only provide evidence (a failing test, a
  dispute, a review finding with a category).

## Alternatives considered

- **LLM planner.** Flexible, but it can loop, skip a check or "decide" a stage passed. Every
  routing rule we need is a function of check results that code can compute. A planner would add
  a model call per transition and a failure mode we would then need a check for.
- **Self-dispatching runs (`gh workflow run` at the end of a review).** Works, but the loop bound
  lives in a counter that a bug can reset, the trace of one issue is split over several runs, and
  a dispatch storm is possible. Rejected.
- **One big job for all six stages.** Simplest, but then the reviewer runs on the same VM as the
  builders and inside the same token scope. Rejected because of ADR-008.

## Consequences

- The maximum number of review rounds is a property of the YAML (three calls exist, no more), not
  of a variable: the loop bound cannot be exceeded by a bug.
- One trigger = one Actions run = one page that shows every round, job and artifact, which makes
  runs easy to follow and link from `runs.md`.
- Duplicated round calls in YAML are a small maintenance cost; changing the round limit means
  editing the caller.
- A reusable workflow cannot be called more than the 4-level nesting limit and a run is limited to
  20 reusable-workflow calls; we use 3.
