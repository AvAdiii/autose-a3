# ADR-008: The reviewer is isolated by job, VM, credentials, model, prompt and input, and must show evidence to approve

- **Decision area:** D8, reviewer independence
- **Status:** Accepted (2026-11-21); context isolation is tested in experiment E1

## Context

A reviewer that reads the implementer's spec, design and test report tends to check that the code
does what the builders *said* it should, and inherits their misreading of the issue. A reviewer
that "approves everything" is worthless, and one that "requests changes on everything" burns the
two rework rounds. The assignment requires: only the issue, the diff and the repository at the PR's
latest commit; read and run, never push.

## Decision

Independence is enforced in six layers, each of which would be enough to break one failure mode:

1. **Own job, own VM.** The review job starts from a fresh runner; nothing from the build job's
   disk exists there. It does not download any build artifact.
2. **Own credentials.** `permissions: contents: read, pull-requests: write`. Checkout with
   `persist-credentials: false`; the reviewer process gets no GitHub token in its environment.
   `review.py` posts the review after the reviewer exits. The PR is authored by the
   `autose-dev-avadiii` App, the review by `github-actions[bot]`: different identities, so a formal
   `APPROVE`/`REQUEST_CHANGES` is possible and is never a self-approval.
3. **Own input.** The prompt contains the issue (title, body, maintainer comments), the output of
   `git diff base...head`, and a note that the repository at head is in the working directory.
   It does **not** get `spec.md`, `design.md`, `test_report.md`, `pr.md` (the PR body) or any
   transcript.
4. **Own model.** `claude-opus-5-5`, different from the builders' Sonnet (ADR-006).
5. **Own prompt.** Written as a maintainer deciding whether to merge: derive your own acceptance
   checks from the issue *before* reading the diff, then verify each one by running code; review
   architecture fit against `ARCHITECTURE.md`; look for regressions outside the changed lines.
6. **Evidence-carrying verdict.** Output is JSON (`--json-schema`): per derived check, `how
   verified` (command run) and `result`; blocking findings need `file`, `evidence` and a `category`
   (`requirements`, `design`, `implementation`, `testing`). An `approve` with zero executed
   verification commands is rejected by `review.py` and re-requested once.

**Against rubber-stamping.** The prompt states the base rate honestly ("about half of automated PRs
in this repository need changes"), forbids approving on the strength of the PR's own tests alone,
and requires at least one probe the PR's tests do not cover. We measure the reviewer on five
seeded PRs with known labels (`experiment/seeded_prs/`), four defective and one correct, so both
missed defects and false rejections are counted.

## Alternatives considered

- **Same job, separate session.** Cheaper (no new VM), but the reviewer could read `.autose/out/`
  on disk and would share the job token. Rejected.
- **Reviewer sees spec and design** ("so it knows what was intended"). This is the variant tested
  in E1; the expectation is that it reduces detection of spec-level misreadings.
- **Reviewer can push fixes.** Faster loops, but then the reviewer is a second implementer that
  reviews its own work. Rejected.

## Consequences

- The reviewer re-derives intent from the issue, so it also reviews the analyst's interpretation.
- Opus on a fresh VM costs an extra setup (~1 min) and the most expensive tokens per call.
- With only five seeded PRs the measured detection rate has wide uncertainty.
